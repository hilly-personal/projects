# Feature Roadmap — Tender Intelligence Platform

Living roadmap, edited directly (by you or with me) as the project evolves. Status annotations
below reflect what's actually been built and verified in this repo as of 2026-09-05 — everything
else in this list came from your own competitor-matrix research, which I haven't independently
verified in this session (see the "Open questions" section at the bottom, which already flags
this — worth resolving before treating competitor-claim items as settled fact).

## Tier 0 — Parity (must-have to be a credible switch target)
- [~] Full source ingestion: official public tenders + scraped private-sector opportunities (match Yfat/Govo breadth)
  — **Partially built**: live scraping of mr.gov.il's real public tender search is done and verified (`src/ingestion/scrape_open_tenders.py`, runs every 8h), but deliberately scoped to our 7 validated domains, not full nationwide/private-sector breadth — that's a much larger undertaking (hundreds of individual municipal/institutional sites) that was explicitly descoped this round in favor of starting small.
- [~] Category taxonomy, ~70+ branches (currently narrower than this — needs expansion)
  — We're at 7 validated domains (cleaning, security, catering, gardening, laundry, transport, parking), each individually precision-checked against real title samples. Parking (`שירותי חניה`) added 2026-09-05: 1,591 title matches, 211 distinct companies, 25/25 clean on a random precision sample. Pest control, waste/garbage removal, and events were all tried and rejected the same discipline (agricultural-research contamination, hazardous/medical-waste contamination with only 27 thin suppliers, and complete heterogeneity, respectively). Expanding further means repeating that same per-domain precision-sampling discipline, not just adding keywords.
- [~] Category-based smart alerts: email / SMS / push
  — **Partially built**: weekly change-detection + email digest pipeline is coded and wired to a real Resend account (`src/pipeline/detect_changes.py` + `send_digests.py`), verified against a real first snapshot in production. Still needs a second real week-over-week run to prove an actual diff-triggered email end-to-end. No SMS/push.
- [ ] Structured, filterable premium fields: budget/financial scope, contractor license tier, document cost, location — done as real filters, not a locked "field exists" teaser
  — Location and deal-size-quartile filters exist in the onboarding flow, backed by real data (buyer→district mapping, quartile buckets computed server-side). Contractor license tier and document cost aren't in any source data we have — would need a new source, not just a UI filter.
- [x] "New since your last visit" indicator on the open-tenders feed — a badge/count of how many new listings were added since the user last checked
  — **Built and tested** (2026-09-05): badge on the open-tenders section header compares `open_tenders.first_seen` against a remembered last-visit date — server-side (`user_scopes.open_tenders_last_visit`) for signed-in users, localStorage for anonymous visitors. Date-level granularity (matches `first_seen`'s own precision): a first-ever visit never claims "all tenders are new," and a same-day repeat visit doesn't re-flag that day's batch. Verified via a real happy-dom DOM test covering all 4 paths (first visit, returning anon visitor, same-day repeat, signed-in server-side). Needs `webapp/supabase/add_open_tenders_last_visit.sql` run once against Supabase, then a redeploy of `webapp/`.

## Tier 1 — Wedge (differentiation — nobody in the matrix does these)
- [~] Real fit-scoring against company profile (past bids/wins, licenses, sector) — replaces keyword "smart agent" matching
  — The renewal-signal model (`gap_flag`/`short_ext_flag`/`final_option_flag`/tier classification) is a real, working version of this for the *exemptions* data, not yet extended to a full "company profile" concept.
- [ ] Structured budget-tier filtering + historical award benchmarking ("similar tenders closed at ₪X–Y")
  - ⚠️ **Gate, already partially informed by this session's own findings**: we already hit exactly the failure mode this flags — the government amount field carries a literal "1" placeholder for undisclosed amounts (handled: floored at ₪1,000 before computing medians), and the bulk Tenders export's award/supplier fields were found >99% empty in the original Phase 1 investigation. Any budget-benchmarking feature needs the same fill-rate audit discipline already applied elsewhere before trusting it.
- [ ] Win-probability signal: incumbent-holder detection, competitor density, historical win rate by category
  — Incumbent-holder detection exists in spirit (`latest_buyer`, tier/volume-based classification on the magic-quadrant chart); true win-probability scoring doesn't.
- [ ] AI eligibility-checklist + deadline extraction from tender documents
  — Deadline *extraction* for open tenders is done (`submit_start`/`submit_end` scraped directly from mr.gov.il's real detail pages). Document-level eligibility-checklist parsing is not.
- [ ] Automated first-draft bid sections (compliance/qualification boilerplate) — targets the Yfat Radar / Govo consultant / Maagarim add-on revenue line
- [ ] For subscribed users: approximate cost to bid per tender (document-purchase fee + any required bid guarantee/deposit) — real submission-associated costs, not the contract value itself
  — Not yet verified whether mr.gov.il's tender detail pages expose this at all (we only confirmed title, buyer, and submission dates so far — see `scrape_open_tenders.py`). Needs the same discipline as everything else scraped this session: check real detail pages for a document-cost/guarantee field before assuming it's extractable, rather than building UI against an assumed field.
- [ ] Direct "submit/bid" link on each open-tender card, not just a link to the detail page
  — Today's open-tenders cards link to `t.detail_url` (the tender's mr.gov.il detail page — `src/ingestion/scrape_open_tenders.py`), which shows the submission window dates but hasn't been checked for a *separate* actual submission-portal URL (a distinct "הגשת הצעה" link/system, if mr.gov.il even exposes one outside the detail page). Needs a real check against a live detail page before assuming a one-line link swap covers it — same discipline as the document-cost item above.

## Tier 3 — Vertical & adjacent expansion
- [ ] Construction vertical pack (contractor-classification-aware, site-visit dates, bank-guarantee amounts)
- [ ] Lightweight competitor/market intelligence (who's winning, at what price) using Tier-1 award data
- [ ] API/CRM integration (Salesforce, monday.com, Priority)
- [ ] Tender-lawyer marketplace: a second, distinct user type (lawyers, not contractors) who subscribe to get matched with contractors requesting tender assistance or submission help, billed per engagement rather than the flat contractor subscription
  — A real two-sided marketplace, not a feature toggle on the existing product: needs (1) a lawyer account type/role separate from `user_scopes`, (2) a request/matching flow (contractor asks for help -> relevant lawyers notified), (3) per-engagement billing distinct from Cardcom/Tranzila's single-sided flat subscription (a marketplace commission or per-case invoice model, not yet designed), and (4) real legal/liability scoping — this platform would be introducing/facilitating a professional-services relationship, not just showing data, which is a different liability posture than anything shipped so far.

## Discoverability (SEO / GEO)
Full plan: `discoverability_architecture.md` (drafted 2026-09-05). Summary of the top tasks, in
the order the plan itself recommends — schema/naming first (cheap), buildout gated behind the
pricing/demand validation already flagged in Open Questions below.
- [ ] Lock the canonical URL scheme now: `/tenders/{category}/{publication_number}` (open tenders —
  already fully public data), `/buyers/{id}` (a new stable buyer entity), `/domains/{category-key}`
  (reuses the existing `DOMAINS` keys). Naming-only, near-zero cost, prevents future data-model
  collisions — do this regardless of when the actual pages get built.
- [ ] Add a real `buyers` table (id, name, district) — the one genuine schema gap. Today buyers are
  matched by exact string against `buyer_regions`, not a real entity with a stable id/slug.
- [ ] Static-HTML build step in the existing pipeline (`refresh_all.py`/GitHub Actions) — `webapp/`
  is a client-side SPA today, so a crawler hitting any URL gets the JS shell, not content. The fix
  reuses the pipeline that already regenerates JSON on a schedule, not a new rendering framework.
  ⚠️ **Gate**: hold until the pricing/demand open questions below are resolved — building the growth
  channel isn't how the underlying product's paying demand gets validated.
- [ ] Pilot with open-tender pages only, before committing to the larger buyer-page long tail —
  lowest risk (data's already fully public, dozens not thousands of rows today), cheapest way to
  learn whether this channel produces any real signal at all.
- [ ] Buyer pages (aggregate counts only — tier/active-count, never a named supplier's specific
  buyer/date/amount) + category hub pages (reuses `market_stats`, already computed) — full buildout,
  same gate as the build step above.
- [ ] schema.org structured data — `GovernmentOrganization` for buyer pages, `BreadcrumbList`
  everywhere, `ItemList` for category hubs. No forced schema type for individual tenders (schema.org
  has no clean "government procurement opportunity" type — don't mark up a claim the page doesn't
  support). Only after page buildout is actually greenlit.
- **Explicit boundary, not a task**: individual company/supplier pages stay non-public — a full
  page would hand this product's actual paid value (a named supplier's buyer relationships, dates,
  amounts) to search crawlers and competitors for free. A thin, fact-free signup-CTA stub is the
  ceiling there, not a growth asset in its own right.

## Tech debt
- [ ] Multi-category support, end to end — both the first-run onboarding page and the opportunity feed's own scope-editing sheet let a visitor multi-select categories and preview a combined live match count, but the ACCOUNT-level scope (`SCOPE.category`, the server-side `user_scopes.category` column) stays single-category throughout — confirmed real: that column is a scalar `text`, not an array, and three other things key on a single active category too: the magic-quadrant chart's bucket ranking (`ntile()` computed server-side `partition by category`), the digest/change-detection pipeline (`company_snapshots`/`change_events`), and most `app.js` fetch/filter call sites (though those are mostly one-line `.eq` → `.in` swaps). The feed's own multi-category browsing filter (`feedApplied`, localStorage-only, `ti_feed_scope`) is real and works today — it's the account-level persistence (digest emails, saved scope) that's still single-category. Doing this properly needs: (1) a `user_scopes.category` → `categories text[]` migration, (2) updating `detect_changes.py`/`send_digests.py` to loop per category, (3) either a per-category tab/selector on the magic-quadrant chart or a real cross-category bucket re-derivation. Not done in this pass — tracked here per an explicit product decision, not forgotten.
- [ ] Real ₪ median contract value for the onboarding live panel and the feed's aggregate stats — currently shows the most common size-quartile bucket among matching companies (honest, zero new backend), not a literal ₪ figure, because anon visitors only ever get `dealsize_bucket` (1–4), never a raw amount (schema.sql deliberately withholds it to avoid leaking an exact company's contract value). A real aggregate median would need a new anon-safe view/RPC exposing a median per (category, region, dealsize-bucket) — never per-company. Per-card "estimated value" in the feed IS a real ₪ figure for signed-in/sub users (`latest_amount`, floored the same as the quadrant median) — this item is specifically about the anonymous-safe aggregate stats.
- [ ] Real "new since last visit" tracking for the opportunity feed — deliberately NOT built this pass (unlike the open-tenders feed's own real version, which compares `first_seen` against a stored last-visit date). The design's own "new" badge was really just "top-3-by-confidence" mislabeled as new, which would have been a fabricated claim — dropped rather than shipped. A real version needs the server-side `change_events` table (already written by `detect_changes.py`) exposed to the frontend, which nothing reads today.
- [ ] The feed's "עקבו" (track/watchlist) button is a stub for signed-in users (visually present, does nothing) — real watchlist/pipeline tracking is a Tier 2 item, not built yet.
- [ ] No "you are here" marker on the market map — the design shows one at a fixed, made-up position; dropped entirely rather than shipped, since this app has no real signal anywhere for "which company is the current visitor" (no such field is captured at signup). Buildable for real only if/when a subscriber ever identifies which company is theirs.
- [ ] Market map's "top 10 leaders" leaderboard is signed-in-only (anon sees a locked note instead) — even anonymized, an exact-₪-ranked top-10 list would be more than the anon tier reveals anywhere else (anon never gets real amounts, only 1–4 quartile buckets), and it's not computable from `companies_teaser` at all (no raw amounts there to rank by).
- [ ] Tender dossier's "SOURCE" citation shows the company's latest procedure id (`latest_proc_id`), not a per-claim citation per numbered reason — the design implies each individual "why" reason links to its own procedure number, but `classifyOpportunityFull`/`Teaser` only ever produce ONE real reason string per opportunity, not a list of independently-sourced claims. Built as one honest why-card with one real source, not multiple fabricated ones.
- [ ] Tender dossier's "PDF" export is the browser print dialog (`window.print()`, same mechanism the individual company report already uses), not a server-generated PDF — no such generator exists. Honest given what's real today; a real branded PDF export would be new backend work.
